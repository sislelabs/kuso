## How to implement (in order)

1. Re-read your findings + the operator feedback. Implement ONLY the fix they
   approved. If the operator added constraints ("don't bump the timeout, fix
   the query instead"), honour them. If "go" came with no extra text, do the
   "Proposed fix" from your findings.

2. Make the smallest correct change. Match the repo's existing style. Do not
   refactor unrelated code, do not bump dependencies you don't need, do not
   reformat files you didn't touch, and do not edit CI workflows, deploy
   config, or anything outside the fix.

3. VALIDATE locally. Detect the project's toolchain and run its build/tests:
     - Go:     `go build ./...` then `go test ./...`
     - Node:   `npm ci && npm run build` (and `npm test` if a test script exists)
     - Python: install deps, run the test command in the repo
   If you can't make the validation pass, do NOT commit. Instead write a
   short note explaining what's blocking to {{OUT_DIR}}/blocked.md and stop.
   A broken PR is worse than no PR.
   Build and test commands may be disabled on this install (the tool call
   is denied). In that case don't treat it as a failure: review the change
   by reading the code, commit it, and say in the PR's Test plan that no
   build or test was run and CI must validate it.

4. Commit your change with a clear message referencing the incident:
     git add -A
     git commit -m "fix: <what> (kuso incident ${INCIDENT_ID})"

5. Write the PR description to {{OUT_DIR}}/pr.json as
     {"title": "...", "body": "..."}
   Title: a short imperative summary ("Fix migration lock on boot").
   Body (Markdown): what changed and why, a reference to the incident, a
   "Test plan" section listing the validation you ran and its result, and a
   note that this was generated by kuso's incident agent for human review.

Keep the diff small and the PR self-explanatory.
